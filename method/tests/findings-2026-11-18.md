> **SERIOUS DEFECT: failure-path pull request F2 MERGED.** PR #26 ("TEST: overlap must fail") branched from `f69bc3a`, set a check on `us_census_mdi`, which PR #25 had already changed on main. The `validate` check passed and the workflow merged it (commit `d30f376`). It should have gone red with "was changed on origin/main since you branched". As a result main now holds a junk value, `chk_link_live_detail: "overlap test"` on `us_census_mdi`, and the run was **stopped** as the brief requires. F1 and T3 to T9 were not run. Not reverted; a maintainer should decide.
>
> Likely cause (not verified): `scripts/validate.py` finds the overlap with `git merge-base HEAD origin/main`. In a pull-request workflow, `actions/checkout` checks out the merge commit, so HEAD already contains main, the merge-base is main's tip, and the diff between them is empty. The check can never fire in CI. Locally, run before the push, it can.

## Defects

1. **F2 merged** (above).
2. **A no-op re-read can raise a tier.** T2 set only `chk_link_live` on `us_census_mdi` after confirming the page was unchanged (PDF only, no data). After the rebuild its `verify_tier` went Bronze to **Silver** and `verified_on` became 2026-11-18. No evidence for any other check changed. `global_diva_gis` stayed Bronze. The tier logic, or the row's earlier values, needs a maintainer look.
3. **Validator rejects what the skill asks for.** Skill section 4: "Every check you set gets `<check>_detail` ... and `<check>_evidence`." Setting `chk_link_live_evidence` fails with "unknown column". I dropped it.
4. **"Closes #24" did not close the claim.** PR #25 merged with the closing reference recorded (`closingIssuesReferences` lists #24), but the issue stayed open. #22 was closed by the workflow ("All items settled" path in `sync_issues.py`). #24's items are still in the `read` queue, because a re-read that settles nothing leaves them offered, so the claim also stays open. Result: a contributor who did the work correctly still has an open claim and the same two items back in the queue (read: 99 free of 100).
5. A contributor-facing `gh pr checks --watch` straight after `gh pr create` printed "no checks reported"; the check appeared about 30 seconds later. Not a defect in the repo; the skill's "watch" step needs a short wait.

## Unclear or wrong instructions

- Skill 6.1 / brief: "tier" for a new dataset could not be checked because every T1 item was ruled out. Nothing says whether `restricted` landing pages (Discuss Data "Restricted access") should be a row with `chk_access: fail` or a ruled-out verdict. I chose `restricted`.
- Skill 3: "Per item: landing page or repository record first, then at most two linked pages." Discuss Data has no record API; I used the DOI resolution page. Unstated whether that counts as the record or the page.
- `queue.py --kind read` calls these "Bronze rows ... unverified", but both items had been page-read on 2026-10-29. "Unverified" in the menu does not match what the rows show.
- `lookup.py --id` prints about 150 lines per row. Skill 1.7 says to use it, which costs a lot of context per item and is not in the token estimate.
- The authoring copy contained an unsubmitted ledger file and an open claim (#21) from an earlier run; the brief says to use a fresh clone, so I did, and left both alone.
- `date` and the "minutes" field: nothing says how to measure minutes when tool calls are slow; I used wall clock.

## Suggestions

1. Make the overlap check use the PR's real base and head (`git merge-base origin/<base> <head sha>`, or `git diff` of the branch's own commits), and add a CI test that must go red for a deliberately overlapping fixture.
2. Add a guard so a ledger file whose rows only refresh `chk_link_live` cannot change a tier, or explain the Bronze to Silver move.
3. Either accept `*_evidence` for `chk_link_live` or drop it from the skill sentence.
4. Close a claim when its PR merges (honour "Closes #n"), or say in the skill that a claim whose items remain open stays open.
5. Let a read that confirms "nothing more to settle" leave the queue, for example with a `blocked` or `settled` flag, so items are not re-offered.
6. Revert the junk `overlap test` value on `us_census_mdi` (PR #26).
